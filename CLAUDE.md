## Database access

- Local PostgreSQL **18.1** (EDB installer), `localhost:5432`, user `postgres`, database **`tech_shop`**.
- The password is in `~/.pgpass` (never write it into any project file).
- Binaries: `/Library/PostgreSQL/18/bin` (should be on PATH; if `psql` is not found, use the full path).
- Run SQL from the project root:
  - a file: `psql -U postgres -d tech_shop -v ON_ERROR_STOP=1 -f <file.sql>`
  - a query: `psql -U postgres -d tech_shop -c "<sql>"`
- For risky or long experiments (bulk data generation, dropping objects) use a scratch database: `createdb -U postgres tech_shop_test`, and say so.
- The team uses DataGrip on the same database — results are visible there immediately.

## Source of truth

- The schema is `00_ddl/ddl_v2.sql`. Never invent tables or columns; check the DDL (or `docs/data_dictionary.md`).
- The ER diagram in Visual Paradigm must match the DDL exactly. Any schema change is made in both places.
- Files in `reference/` (`ddl_project.rtf`, `er_diagram_picture.png`) are the OLD v1 versions — never use them as the schema.
- Every change to the database goes through a `.sql` file in the repo first, then gets executed. Never change the database ad hoc in a way the other members cannot reproduce from the scripts.

## Conventions

- Object names: English, `snake_case`. SQL comments and all documentation: **Macedonian (Cyrillic)**.
- `orders`, never `"order"` (reserved word).
- Keys: `GENERATED BY DEFAULT AS IDENTITY`; `BIGINT` for large tables (orders, order_item, serial_number, shipping, installments, price_history, review, returns, customer_support_report, wishlist_items).
- Naming: `fk_<table>_<target>`, `uq_<table>_...`, `chk_<table>_...`, `idx_<table>_<columns>`, views `v_`, functions `fn_`, procedures `sp_`, triggers `trg_`.
- Line price always from `order_item.unit_price`, never from `product.price`.
- Foreign-key indexes are intentionally missing from the DDL — they are added in Phase 3 with before/after measurements.
- Scripts must be re-runnable (`DROP ... IF EXISTS`, `CREATE OR REPLACE`).

## Documentation — mandatory on EVERY change

The mentors grade from `docs/`. Documentation is part of the work, not an afterthought.
A task is NOT done until the docs are updated.

After any change you make, in the same task:

1. **Phase document** — update the relevant `docs/0X_*.md` (what was done, why, how it was verified, results). Follow the section structure already in that file.
2. **CHANGELOG** — add an entry at the top of `docs/CHANGELOG.md`: date, phase, member (ask if unknown), files changed, what changed and why.
3. **Schema changed?** Then also:
   - write a migration `00_ddl/NNN_<desc>.sql` AND apply the same change to `00_ddl/ddl_v2.sql`;
   - run `psql -U postgres -d tech_shop -X -A -t -q -f scripts/data_dictionary.sql -o docs/data_dictionary.md`;
   - re-run `00_ddl/constraint_tests.sql` and add tests for new constraints;
   - list what must change in the ER diagram (Visual Paradigm is edited by hand).
4. **Status** — if a phase status changed, update the table above and `docs/README.md`.

Documentation rules:

- Language: Macedonian (Cyrillic). Code, identifiers and SQL stay in English.
- Write for a mentor who has not seen the code: explain the reasoning ("зошто"), not only the result.
- Every number in the docs comes from an actual run (row counts, timings, EXPLAIN). Paste real output in code blocks; never invent results.
- Phase 3: for each view — query, EXPLAIN (ANALYZE, BUFFERS) before, change, EXPLAIN after, a before/after table (average of 3 runs after `ANALYZE`), conclusion — including cases where an index did NOT help. Follow the example document provided on the course page.
- Phase 4: for each object — purpose, signature, logic, example call, test (success and failure) with real output.
- Save raw outputs (EXPLAIN, test runs) under the phase folder and reference them from the doc.
